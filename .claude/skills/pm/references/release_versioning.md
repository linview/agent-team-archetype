# 发布版本规划细则(release versioning)

> SKILL.md §6 的按需加载细则。本文件是**通用能力**:适用于任何遵循 semver 2.0.0 + Keep a Changelog 约定的工程,不绑定特定发布脚本或工程结构。

## 1. 适用前提

- 工程对外交付物有版本号(库 / CLI / 服务 / skill 包 / 制品均可)
- 版本号遵循 [semver 2.0.0](https://semver.org/);变更记录遵循 [Keep a Changelog](https://keepachangelog.com/)

若工程无 CHANGELOG,pm 应先推动建立(最小约定:版本头 + 变更分类),再谈定版。

## 2. 版本粒度收集方法

定版依据是**发布内容相对上一轮 release 的整体**,不是单条 commit:

1. 定位上一轮 release 基线:最近一个定版头(`## [vX.Y.Z] - date`)或 git tag
2. 收集基线以来的变更面:
   - CHANGELOG `[Unreleased]` 条目(首选)
   - `git log <last-release>..HEAD --oneline`(补充)
   - 本 Sprint 已收口 Story 清单(交叉核对)
3. 对每条变更问三个问题:
   - 删了或改了**对外可依赖的东西**吗?(API/命令行参数/配置格式/输出格式/能力语义)→ MAJOR 信号
   - **新增**了对外能力吗? → MINOR 信号
   - 只是修 bug / 改文档 / 内部重构? → PATCH 信号
4. 多种信号并存时**就高不就低**(同时含 MINOR 与 PATCH → MINOR;含 MAJOR 信号 → MAJOR)

## 3. semver 2.0.0 边界情形

| 情形 | 规则 | 示例 |
|------|------|------|
| 初始开发期 | 0.y.z:任何变化都可能破坏;0.1.x → 0.2.x 可含破坏性变更,不必 MAJOR | v0.3.2 → v0.4.0 |
| pre-release | 版本号后加 `-` 标识,优先级低于正式版;不确定变更粒度时先出 pre-release 收集反馈 | v2.8.0-rc.1 |
| build metadata | `+` 后缀,不参与优先级比较 | v2.8.0+build.5 |
| 破坏性 bug fix | 修复 bug 但改变了对外契约(如返回结构)→ 按 MAJOR/PATCH 语义判断,修契约=修 bug 但破坏兼容仍是 MAJOR 信号 | — |
| 立即热修 | 在 pre-release 基础上修复 → 递增 pre-release 段,而不是另起 PATCH | v2.8.0-rc.1 → v2.8.0-rc.2 |
| 0.y.z → 1.0.0 | 工程对外承诺稳定的标志,由用户/团队显式决策,不是自然演进 | v0.9.3 → v1.0.0 |

## 4. 定版 checklist

定版(触发发布)前逐项确认:

- [ ] 上一 release 基线已确认(tag / CHANGELOG 定版头)
- [ ] 基线以来全部变更已收集并归类(MAJOR/MINOR/PATCH 信号)
- [ ] 版本号已按判定表确定,多信号就高
- [ ] CHANGELOG `[Unreleased]` → `## [vX.Y.Z] - YYYY-MM-DD`,历史版本头分节完整(无条目错误并入)
- [ ] 涉及破坏性变更时,升级指引已写入 CHANGELOG
- [ ] 发布执行方(dev/commit/devops)已知悉版本号与发布内容范围
- [ ] 发布后验证计划就绪(产物完整性/门禁或测试证据/内容抽查)

## 5. 反模式(常见错误)

| 反模式 | 后果 | 纠正 |
|--------|------|------|
| 按发布日历定版本(时间到了就 MINOR) | 版本号失去信息量,消费者无法从版本判断风险 | 回到变更粒度判定 |
| 单条 commit 看起来小就定 PATCH,忽略同包内的新能力 | 新能力被 PATCH 掩盖,下游错失升级动机 | 按发布内容整体判定 |
| 执行发布脚本的人顺手定版 | 定版权漂移,版本号无人负责 | 定版权在 pm,执行者遇到未定版应暂停上报 |
| `[Unreleased]` 未定版就触发发布流程 | 依赖版本号解析的发布机制可能取错版本(如穿透到更旧版本头) | 定版是发布的前置条件 |
| 版本头写了但历史版本分节丢失 | 变更历史并入错误版本,追溯失真 | 定版时核对分节完整性 |

## 6. 与其他角色的协作

- **pm**:定版决策、CHANGELOG 定版、发布内容范围确认(本 skill §6)
- **commit**:按定版结果提交 CHANGELOG 收口 commit;建 MR 走评审
- **dev/devops**:按工程自有发布机制执行;发现版本未定或不一致时暂停并上报 pm,不自行更改版本号
- **qa**:发布后验证的证据产出(测试报告/门禁结论)归档,支撑下一轮基线确认
