# AC 测试分层策略

## 核心原则

**测试要求跟随实现阶段，不超前不遗漏。**

Story AC 中的测试责任必须根据**当前实现阶段可达的测试类型**来设定。不可达的测试类型不应作为 Story 关闭条件，但应在后续阶段的 Story AC 中体现。

## 实现阶段与测试可达性

```
实现阶段               可达测试            AC 测试要求
─────────────────    ────────────────   ──────────────────
代码编写中             UT                  UT 覆盖率达标，通过率 100%
API 端点就绪           API 测试            API 契约测试通过
服务/数据集成          SIT                 集成场景测试通过
前后端协同部署完成      E2E                 前后端联调验证通过
完整系统（含真实数据）   UAT                 用户场景验收通过
```

### 实现阶段 × 测试分层矩阵

| 实现阶段 | UT | API | SIT | E2E | UAT | 说明 |
|---------|----|----|-----|-----|-----|------|
| 代码编写中 | 可达 | - | - | - | - | 只有代码，无外部依赖 |
| API 端点就绪 | 可达 | 可达 | - | - | - | Handler 可独立测试 |
| 服务/数据集成 | 可达 | 可达 | 可达 | - | - | 集成环境可用 |
| 前后端协同部署 | 可达 | 可达 | 可达 | 可达 | - | 完整技术栈可用 |
| 完整系统 | 可达 | 可达 | 可达 | 可达 | 可达 | 含真实数据 |

## 功能粒度与测试要求

不同类型的功能需要不同的测试策略。PM 在拆解 Story 时，应根据功能所属层级确定最低测试要求。

### 功能粒度 × 测试分层矩阵

| 功能类型 | UT | API | SIT | E2E | UAT | 说明 |
|---------|----|----|-----|-----|-----|------|
| 基础设施（配置/容器/CI） | 必须 | - | 可选 | - | - | 非业务功能，验证配置正确性 |
| 数据层（DAO/Repository） | 必须 | - | 必须 | - | - | 数据访问逻辑依赖集成测试验证 |
| 服务层（Service/Logic） | 必须 | - | 可选 | - | - | 业务逻辑核心，UT 优先 |
| API 端点（Handler/Router） | 必须 | 必须 | 必须 | - | - | 接口契约需三层验证 |
| 前端页面（组件/视图） | 可选 | - | 必须 | 必须 | 必须 | 用户体验关键，依赖多层验证 |
| 跨域集成（关联/编排） | 必须 | 必须 | 必须 | 必须 | 必须 | 最高风险，全层验证 |
| 部署集成（Docker/Helm） | 可选 | - | 必须 | 必须 | - | 环境一致性和联调验证 |

**图例**：
- **必须**：Story AC 中必须包含该层测试要求
- **可选**：视复杂度决定是否包含
- **-**：该层测试不适用此功能类型

## AC 测试标签规范

每个 Story 的验收标准分为**功能标准**和**测试标准**两部分。测试标准使用标签前缀标识测试层级。

### 标签定义

| 标签 | 测试层级 | 适用条件 | 典型要求 |
|------|---------|---------|---------|
| `[UT]` | 单元测试 | 代码编写阶段即可执行 | 覆盖率达标，通过率 100% |
| `[API]` | 接口测试 | API 端点就绪后可执行 | 正常/异常/边界路径覆盖 |
| `[SIT]` | 集成测试 | 服务和数据集成后可执行 | 跨模块交互正确性 |
| `[E2E]` | 端到端测试 | 前后端协同部署后可执行 | 前端→API→数据完整链路 |
| `[UAT]` | 用户验收测试 | 完整系统可用后执行 | 用户场景端到端验证 |

### AC 示例

```markdown
## 验收标准

### 功能标准
- [ ] 按 work_item_id 查询返回关联 MR 列表
- [ ] 查询结果支持分页（page_size/page_num）
- [ ] 无关联数据时返回空列表而非错误

### 测试标准（按实现阶段）
- [ ] **[UT]** Service 层 UT 覆盖率 >= 75%，全部通过
- [ ] **[API]** Handler 测试覆盖正常/异常/边界路径
- [ ] **[SIT]** 集成环境下三表 JOIN 正确性验证
```

### 标签选择指南

PM 在编写 Story AC 时，根据功能类型从矩阵中选择必须的标签：

1. 确定功能类型（基础设施/数据层/服务层/API 端点/前端/跨域/部署）
2. 查功能粒度矩阵，确定哪些标签是"必须"
3. 查实现阶段矩阵，确认当前阶段哪些标签可达
4. 只在 AC 中包含**当前阶段可达**且**功能类型必须**的标签

## Story 状态与测试阶段

Story 状态流转中，每个状态变更必须验证对应层级的测试通过。

| 状态 | 可达测试 | 不可达测试 | 必须通过的标签 |
|------|---------|-----------|--------------|
| IN_PROGRESS | UT | API, SIT, E2E, UAT | `[UT]` 系列全部通过 |
| IN_REVIEW | UT, API | SIT, E2E, UAT | `[UT]` + `[API]` 全部通过 |
| TESTING | UT, API, SIT | E2E, UAT | `[SIT]` 系列全部通过 |
| TESTING(E2E) | UT, API, SIT, E2E | UAT | `[E2E]` 系列全部通过 |
| COMPLETED | 全部 | - | `[UAT]` 系列全部通过 |

**铁律**：不可达的测试标签不作为当前状态的阻塞条件，但必须在后续状态的 Story 中体现。

## 覆盖率基准

| 测试层级 | 覆盖率目标 | 统计范围 |
|---------|-----------|---------|
| UT | >= 75% | Service/Logic 层（剔除数据访问层） |
| API | 100% 端点覆盖 | 所有已实现 API 端点 |
| SIT | 关键场景 100% | 跨模块交互、数据正确性 |
| E2E | 核心用户链路 100% | 前端→API→数据完整路径 |
| UAT | 用户故事 100% | PRD 定义的验收场景 |

## 注意事项

1. **不超前要求**：Sprint 早期阶段不要在 AC 中要求 SIT/E2E/UAT，因为依赖尚未就绪
2. **不遗漏要求**：每个功能类型的"必须"标签最终都必须在某个 Story 中被覆盖
3. **测试 Epic**：如果功能 Epic 无法覆盖所有测试层（如前端 E2E），应在后续 Epic 中安排专门的测试 Story
4. **内容中立**：测试策略适用于任何技术栈，具体框架（Jest/Vitest/pytest/go test）根据项目选择
