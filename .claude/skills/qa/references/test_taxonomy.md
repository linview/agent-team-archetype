## 1. 判型流程（拿到用例先走这四步）

**适用范围**：专项测试选型/定型、判型争议仲裁、误标纠正。功能开发测试的日常用例**不走本流程**——归属与目录由五层金字塔决定（见 §5），功能测试默认即 E2E 类。

对进入判型的测试（已有的或待写的），按顺序回答四个问题。**禁止跳到第 3 步之前就下类型结论**——多数误标源于先看输入随机性。

```
Step 1  问 oracle：这条测试用什么判断通过/失败？
        ├─ 业务预期（精确值/路径/内容）        → E2E
        ├─ 数据非空/字段映射/链路通（巡检）    → E2E（@probe 子类）
        ├─ 崩溃即 bug（不崩就算过）            → Monkey
        ├─ 不违契约（畸形输入被优雅拒绝）      → Fuzz
        ├─ 数学不变量（性质永远成立）          → PBT
        └─ 无泄漏（内存/CPU/句柄不增长）       → Stress
Step 2  问输入：怎么来的？（仅作修饰词，不决定类型）
        固定/构造 | 畸形 | 框架生成 | 高频连续 | 随机游走
Step 3  定类型：Step 1 的结果即类型；Step 2 只影响描述
Step 4  双检：若 Step 1 答「数学不变量」且输入随机 → PBT（不是 monkey）
        若 Step 1 答「崩溃即 bug」→ monkey（无论输入是否结构化）
```

**判型口诀**：先问「用什么判断对错」（oracle），再问「输入怎么来」（生成方式）。

**示例**：

| 待判测试 | Step 1 oracle | 判型 | 常见误标 |
|---|---|---|---|
| 表格行数 vs API 字段一致 | 数据非空/映射 | **E2E @probe** | ❌ monkey（因目录叫 monkey/） |
| 随机字符串输入解析器，断言不崩或报错 | 不违契约 | **Fuzz** | ❌ monkey（因输入随机） |
| `reverse(reverse(x)) == x` 跑 1000 组随机 x | 数学不变量 | **PBT** | ❌ monkey（因输入随机） |
| 点导出按钮断言下载了文件 | 业务预期 | **E2E @sanity** | ✅ 无误标风险 |

## 2. 归属与 CI 策略（判完型后做什么）

判型后立即执行对应行。目录与 CI 策略是判型的**直接输出**，不是独立决策。

| 类型 | 归属动作 | CI 策略 | 何时写它 |
|---|---|---|---|
| **E2E @sanity** | `tests/e2e/`，marker `@sanity` | 每次提交跑（`--grep @sanity` job） | 覆盖核心正向路径 |
| **E2E @probe** | `tests/e2e/`，marker `@probe` | **不进 CI**——手动/定期巡检/发布前 | 验证数据准确性（生产） |
| **Monkey** | 功能校验型项目**默认不写**；crash 发现型（编辑器/游戏/复杂数据处理）才立项 | 独立 job，低频 | 有 crash 风险面时 |
| **Fuzz** | 后端 API 输入边界（非 UI）；无解析器可暂缓 | 独立 job 或工具链 | 有输入解析/反序列化面时 |
| **PBT** | SIT 交叉验证形态：断言「服务层结果 == 数据层结果」（见 SKILL.md SIT 节） | 随 SIT 跑 | 有跨层一致性诉求时 |
| **Stress** | 归 monkey stress 子集；单独资源监控 | 独立 job | 有内存/句柄敏感逻辑时 |

**@probe 连生产而非测试环境的理由**（一行版）：测试环境数据稀缺会把「数据缺失」误报成「服务层 bug」；连生产才能区分两者——与 SIT 交叉验证「数据层有数据 + API 返回空 → 服务层 bug」同源。

**@probe 不进 CI 的理由**（一行版）：连生产慢 + 生产数据变动引入 flaky + CI 是回归门禁而 probe 是巡检，职责不同。

## 3. 已知 bug 标注规程（test.fixme）

**发现未修复 bug 时，按此序列操作**（不要注释掉、不要 test.skip）：

1. 记 issue：`docs/scrum/issues/issue-YYYYMMDD-slug.md`（编号 `ISSUE-YYYYMMDD-NNN`，见 pm skill Issue 规范）
2. 写 probe test 复现它，标题含 ISSUE 编号（如 `test('export table not empty [ISSUE-20260815-001]', ...)`）
3. 标 `test.fixme`——CI 保持绿（跳过 + expected failure 标记），但报告可见
4. bug 修复后：grep ISSUE 编号找到该 test → 去掉 `.fixme` → 自动转正为回归门禁（复发即红）

**为什么必须 test.fixme 而非 skip/注释**：

| 方式 | CI 行为 | 修复后 | 追溯 |
|---|---|---|---|
| `test.skip` | 跳过，不报告 | 手动改回 | 无 |
| 注释掉 | 不执行 | 手动恢复 | 无 |
| **`test.fixme`** | 跳过 + 报告可见 | 去 `.fixme` 自动转门禁 | ✅ 标题含 ISSUE 编号可 grep |

> test.fixme 与 ISSUE 编号对照表由项目在测试目录维护（如 `tests/e2e/probe/README.md`）。

## 4. 误判检查清单与纠正表

**写完/审完一批测试后过一遍**——任一命中即误标，按右列纠正：

- [ ] 目录/文件名含 "monkey"，但测试体里有业务断言（行数/路径/内容）？→ 它是 **E2E @probe**，改名归位
- [ ] 因「输入是随机的」标成 monkey，但断言是不变量/契约？→ **PBT**（不变量）或 **Fuzz**（契约）
- [ ] 因「输入是随机的」标成 PBT，但断言只是「没崩」？→ **Monkey**
- [ ] 断言「服务层结果 == 数据层结果」却放在 e2e 目录？→ **SIT 交叉验证**（PBT 形态），移入 `tests/sit/`
- [ ] @probe 进了 CI 且偶发红？→ 移出 CI（连生产巡检不进回归门禁）
- [ ] 用 `test.skip` 或注释处理已知 bug？→ 改 `test.fixme` + ISSUE 编号

**历史教训（一段版）**：某项目 monkey 目录下整批脚本实际配强 oracle（行数/路径/业务预期断言），全部误标——根源是按「文件位置/输入随机性」命名而非按 oracle 分类。**判别标准永远是 oracle 来源。**

## 5. 双维度定位：金字塔第一优先级，分类学适配专项测试

**适用前提（先读这段再走 §1 判型）**：功能开发测试领域，分层测试金字塔（UT→API→SIT→E2E→UAT）是第一优先级——测试规划、目录归属、覆盖率、回归门禁全由金字塔主导，**功能测试的日常用例不做分类学判型**（功能测试默认即 E2E 类：业务预期 oracle）。分类学在两个场合登场：

1. **功能测试内部的三处渗透**（不改变金字塔主导地位）：@probe/@sanity 子类划分、断言强度原则、SIT 交叉验证（= PBT 形态）
2. **专项测试选型**（功能测试打底之后启动）：

| 专项测试使命 | 适配类型 | oracle |
|---|---|---|
| 性能测试 | **Stress** | 无泄漏（内存/CPU/句柄不增长） |
| 稳定性测试 | **Monkey / Stress** | 崩溃即 bug / 资源泄漏 |
| 随机测试（找崩溃） | **Monkey** | 崩溃即 bug |
| 随机测试（验证健壮性） | **Fuzz** | 不违契约 |
| 性质验证专项 | **PBT** | 数学不变量 |

**两维度正交**：金字塔回答「测多深」（集成深度），分类学回答「用什么判对错」（oracle 来源）。专项测试落地时两者复合（fuzz 后端 API 边界 = 金字塔 API 层 + Fuzz 类），但**顺序上金字塔先行**——分层功能测试打底是专项测试的前提。

```
例：SIT 交叉验证 = SIT 层 + PBT 类（功能测试内的渗透）
    @probe        = E2E 层 + E2E 类（功能测试内的渗透）
    API fuzz      = API 层 + Fuzz 类（专项测试的复合）
```

**口诀**：功能测试金字塔先行，专项测试分类学适配。

**典型误用**：① 用金字塔维度回答「这是不是 monkey」——monkey 是分类学概念，与放哪层无关；② 反过来，功能测试规划时给每条用例判五类——过度判型，功能测试默认即 E2E 类。

## 6. 附录：rationale 速查

- **oracle 决定类型，random 只是修饰词**：随机输入 + 崩溃 oracle = monkey；随机输入 + 不变量 oracle = PBT。oracle 强（精确预期/数学性质）→ 能定位 bug；oracle 弱（崩溃即 bug）→ 只能发现 crash。
- **Monkey 与 PBT 是两极端，混谈是混乱根源**：monkey 的 oracle 弱到几乎没有（程序活着就行）；PBT 的 oracle 极强（每条性质需精确表述）。错配即误设计。
- **功能校验型项目不做 monkey**：诉求是「数据能看、链路能通、跳转准」（强 oracle，E2E @probe 覆盖），monkey 找不到这类问题，且 runner 成本高。crash 发现型项目（编辑器、游戏）才适合。
- **Stress 归 monkey 子集**：同属「弱 oracle，靠监控非业务断言」。
- **Fuzz 对后端不对 UI**：解析器/输入处理的缺陷在后端 API 边界；UI fuzz 投入产出比低。
