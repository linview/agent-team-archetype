## 层级总览矩阵

| 层级 | 核心目标 | 测试对象 | 依赖 | 定位能力 | 用例数 |
|------|---------|---------|------|---------|--------|
| **UT** | 函数/方法逻辑正确性（Mock 是合理手段） | 单元代码（Mock 外部依赖） | 无外部依赖 | 定位具体函数错误 | 最多 |
| **API** | 接口契约验证 + 业务正确性（需主动索取测试数据） | HTTP/RPC 等契约端点 | 运行中的服务 + 测试数据 | 定位接口层问题 | 较多 |
| **SIT** | **数据层 + 后端服务层**联调验证 | DB 直接查询 + API 调用 | 真实 DB + 运行中的服务 | **定位服务层逻辑 bug** | 适中 |
| **E2E** | **数据层 + 后端服务层 + 前端服务层**联调验证 | 驱动前端 API（Playwright） | 完整部署环境 | 验证三层贯通 | 较少 |
| **UAT** | 用户可感知功能场景（全面准确，非仅有数据） | 用户操作流程 | 生产级环境 | 确认功能/数据精准可用 | 最少 |

## UT — 单元测试

### 定义

对单个函数或方法进行隔离测试，使用 Mock 替代所有外部依赖（数据库、网络、文件系统）。

### 核心目标

- 验证**函数级别的逻辑正确性**
- 确保每个分支（if/switch true/false）都被覆盖
- 作为重构的安全网——有 UT 保护的重构 = 安全

### 测试什么

- 业务逻辑函数的输入/输出
- 边界值和异常处理
- 分支覆盖（每个 if/else 路径）

### 不测试什么

- ❌ SQL 语句正确性（Mock 无法验证）
- ❌ 事务完整性（Mock 无法验证）
- ❌ 跨服务集成问题（Mock 隔离了外部依赖）
- ❌ 数据一致性（Mock 返回的是预设数据）

### 覆盖率标准

| 层级 | 目标 | 说明 |
|------|------|------|
| Logic 层（Service/Handler） | ≥ 80% | 核心业务逻辑，高覆盖率价值 |
| Package 层（Utils/Helpers） | ≥ 60% | 工具函数，中等覆盖率价值 |
| 数据访问层（DAO/Repository） | 20-30% | Mock 测试价值有限，真实性验证交给 SIT |

### 局限性

UT 的 Mock 天然无法发现集成问题。如果一个函数在 Mock 环境中返回正确结果，但在真实数据库查询中失败，UT 无法发现——这正是 SIT 要解决的问题。

## API — 接口契约测试

### 定义

对 HTTP API 端点进行黑盒测试，验证接口契约（请求/响应格式、状态码、错误处理）和业务数据正确性。

### 核心目标

- 验证**接口契约**：请求参数、响应结构、状态码符合设计文档
- 验证**业务数据正确性**：返回的数据不仅"存在"，而且"逻辑正确"

### 两层验证标准

**第一层：契约验证（基础）**
```python
# ✅ 验证接口契约
assert resp.status_code == 200
assert body["code"] == 0
assert isinstance(body["data"], list)
```

**第二层：业务正确性（核心价值）**
```python
# ✅ 验证业务数据逻辑
# 不仅仅是"data exists"，而是"data is correct"
node_types = collect_all_node_types(body["data"])
assert "system" in node_types, "依赖树必须包含 system 节点"
assert "commit" in node_types, "app 制品依赖树必须包含 commit 节点"
```

### 测试什么

- 每个端点的正常流程和异常流程
- 参数校验（required、optional、default）
- 响应结构符合 API 元数据文件定义
- **业务数据语义**：返回数据的结构和内容符合业务逻辑

### 不测试什么

- ❌ 服务层内部逻辑（API 测试无法定位 bug 在哪一层）
- ❌ 数据库查询正确性（需要 SIT 交叉验证）
- ❌ 前端 UI 渲染（需要 E2E 测试）

### 关键区分：API 测试 ≠ SIT 测试

```
API 测试：调 API → 验证返回值 → PASS/FAIL（知道有问题，不知道在哪一层）
SIT 测试：查 DB 获取预期 → 调 API 获取实际 → 交叉断言 → 定位服务层 bug
```

### 测试数据管理策略（前置条件）

API 测试从这一层开始，QA **须主动索取测试数据**来支撑业务逻辑验证。无测试数据 = 无法验证业务正确性。

**QA 应索取的测试数据**：

| 数据类型 | 用途 | 索取对象 |
|---------|------|---------|
| 各域典型数据样本 | 验证正常流程业务逻辑 | 开发者（种子数据脚本） |
| 边界数据（空值/超长/特殊字符） | 验证异常处理和容错性 | 开发者（边界测试用例） |
| 跨域关联数据（需求↔MR↔commit↔制品↔pipeline） | 验证全链路数据一致性 | 开发者（全链路种子脚本） |
| 生产数据脱敏样本 | 验证真实场景数据质量 | DBA（脱敏导出） |

**原则**：API 测试的深度取决于测试数据的完备性。如果无法获取充分测试数据，应在报告中明确标注"测试数据不足，业务验证受限"。

### 支持的契约协议

API 测试不限于 HTTP REST，支持多种契约类型：

| 协议类型 | 测试工具 | 适用场景 |
|---------|---------|---------|
| HTTP REST | pytest + requests | RESTful API 契约验证 |
| gRPC/RPC | grpcurl / 自定义 client | RPC 服务契约验证 |
| GraphQL | pytest + gql client | GraphQL schema 验证 |

**原则**：无论协议类型，API 层测试的验证标准一致——契约正确性 + 业务数据正确性。

## SIT — 系统集成测试

### 定义

在真实环境（运行中的服务 + 真实数据库）中，通过**数据层（DB）与服务层（API）交叉验证**，定位服务层逻辑 bug。

### ⭐ 核心目标（最重要的概念）

**SIT 的核心价值不是验证"数据存在"，而是验证"数据层和服务层的一致性"。**

如果数据层（DB 直接查询）可获得正确结果，但通过 API 在服务层无法获得，那就说明**服务层逻辑有 bug**。

### Bug 定位逻辑

```
数据层有数据 + API 返回空     → 🔴 服务层逻辑 bug（数据映射丢失、过滤逻辑错误）
数据层无数据 + API 返回空     → ✅ 数据问题，非代码 bug
数据层有数据 + API 返回数据   → ✅ 正确
数据层无数据 + API 返回数据   → 🔴 数据映射 bug（幻觉数据）
```

### SIT 交叉验证模式

```python
def test_cross_validation_db_vs_api(pg_conn):
    """SIT 交叉验证的标准实现模式"""

    # Step 1: 数据层 — 直接查 DB 获取预期结果
    with pg_conn.cursor() as cur:
        cur.execute("""
            SELECT a.id, COUNT(ca.id) AS link_count
            FROM aip_artifacts a
            JOIN aip_commit_artifacts ca ON ca.artifact_id = a.id
            WHERE a.type = 'app'
            GROUP BY a.id
        """)
        db_result = cur.fetchone()
    assert db_result is not None, "数据层：无预期数据，无法进行交叉验证"

    # Step 2: 服务层 — 调 API 获取实际结果
    resp = requests.get(f"{API_BASE}/artifacts/source-map",
                        params={"artifact_id": db_result[0], "type": "app"})
    api_result = resp.json()["data"]

    # Step 3: 交叉断言 — DB 预期 vs API 实际
    assert len(api_result) > 0, (
        f"服务层 bug：DB 有 {db_result[1]} 条关联记录，"
        "但 API 返回空数据 → 服务层逻辑有 bug"
    )
```

### SIT 测试的分类

| 类型 | 目的 | 示例 |
|------|------|------|
| **数据质量验证** | 验证 DB 中数据的格式、完整性 | commit_hash 是 SHA-1（40位），artifact commit_hash 是 MD5（32位） |
| **业务规则验证** | 验证数据符合业务规则 | app 制品有 commit-artifact 关联（traceability） |
| **交叉验证** | DB 预期 vs API 实际 → 定位服务层 bug | DB 有 commit 关联但 API source_map 无 commit 节点 → 服务层 bug |

### 为什么 SIT 不可替代

| 测试层级 | 能否发现服务层 bug | 原因 |
|---------|------------------|------|
| UT | ❌ | Mock 无法发现真实数据库查询问题 |
| API | ⚠️ | 能发现"有问题"，但无法定位是数据层还是服务层 |
| **SIT** | ✅ | **唯一能定位"服务层逻辑 bug"的层级** |
| E2E | ❌ | 只验证用户可见行为，无法定位 bug 层级 |

### 与 API 测试的关键区别

```
API 测试回答："这个接口有问题吗？"
SIT 测试回答："这个问题出在哪一层？"

API 测试发现 source_map 返回空 → 知道有问题
SIT 测试查 DB 有数据 + API 返回空 → 知道是服务层 bug
```

## E2E — 端到端测试

### 定义

**数据层 + 后端服务层 + 前端服务层**的三层联调验证。触发源来自驱动前端 API（从 UI 操作触发），验证从前端到后端再到数据层的完整链路贯通。

### 与 SIT 的本质区别

```
SIT = 数据层 + 后端服务层（不含前端，触发源是 API 调用）
E2E = 数据层 + 后端服务层 + 前端服务层（三层全覆盖，触发源是前端 UI 操作）
```

SIT 验证的是"后端服务层逻辑正确性"，E2E 验证的是"从前端操作到后端再到数据的完整链路正确性"。

### 核心目标

- 验证**三层贯通**：前端操作 → API 调用 → 后端处理 → 数据查询 → 前端渲染
- 验证**用户可见行为**：点击、交互、页面渲染、数据展示
- 验证**前后端联调正确性**：前端调用 → 后端处理 → 前端渲染的完整链路
- 验证**非功能性指标**：无 JS 错误、无 API 4xx/5xx、关键元素可见

### 典型框架

| 框架 | 特点 | 适用场景 |
|------|------|---------|
| **Playwright** | 多浏览器支持、自动等待、网络拦截 | 主力框架 |
| Cypress | 实时重载、时间旅行调试 | 小型项目 |
| Selenium | 多语言支持、成熟生态 | 遗留系统 |

### E2E 测试子类型

| 子类型 | 目的 | 示例 |
|--------|------|------|
| **API 连通性** | 验证前端可正常调用后端 API | `api-health.spec.ts` — 检查 16 端点可达 + 业务枚举正确 |
| **页面导航** | 验证前端路由和组件渲染 | `navigation.spec.ts` — 侧边栏点击 → URL 变化 → 组件加载 |
| **交互功能** | 验证前端操作触发正确的后端响应 | `cross-tab.spec.ts` — Tab 切换 → API 参数变化 → 数据更新 |
| **Monkey 随机** | 验证三层联调在随机操作下的稳定性 | `monkey-test-strategy.md` — L1/L2/L3 三层猴子测试 |

### 不测试什么

- ❌ 具体函数逻辑（UT 范围）
- ❌ 接口契约细节（API 测试范围）
- ❌ 服务层 bug 定位（SIT 范围）

### 典型 E2E 测试结构

```typescript
test('clicking pkg-type artifact shows warning alert', async ({ page }) => {
  // 1. 通过 API 找到测试数据（数据层参与）
  const artifact = await findNonAppArtifactViaAPI()

  // 2. 访问页面并交互（前端层参与）
  await page.goto('/artifacts')
  await clickRowContaining(artifact.type)

  // 3. 验证 UI 行为（前端→后端→数据层贯通验证）
  await expect(page.locator('.el-alert')).toContainText('不支持源码追溯')

  // 4. 验证无 API 错误（后端层监控）
  expect(apiErrors).toEqual([])
})
```

### E2E 与 API 测试的关系

E2E 通常包含 API 级验证（通过 `page.request.get()` 直接调 API），但核心差异是：
- API 测试：聚焦接口契约和数据结构，不涉及前端
- E2E 测试：聚焦三层贯通（数据+后端+前端），从前端 UI 触发验证

## UAT — 用户验收测试

### 定义

验证**用户可感知的功能场景**，确保服务功能和业务数据**全面准确**。UAT 不是简单的"有数据就行"，而是追求"数据全面、逻辑准确、功能完整"。

### 核心目标

- 确认**业务价值交付**：系统实现了用户期望的功能
- 确认**数据全面准确**：不仅验证"有数据"，更要验证数据覆盖所有业务场景且与数据源完全一致
- 作为**发布门禁**：UAT 不通过 = 不可发布

### 验收标准（强化）

**核心原则**：不只验证"有数据"，更要验证"全面准确"

| 验证维度 | 标准 | 示例 |
|---------|------|------|
| **功能可用** | 用户操作能正确触发完整链路 | 点击"需求检索" → 返回正确需求列表 |
| **数据全面** | 展示数据覆盖所有业务场景 | 需求列表包含所有状态的需求（进行中/已完成/已关闭） |
| **数据准确** | 展示数据与数据源完全一致 | 前端展示的 MR 数量 = 数据库实际 MR 数量 |
| **业务正确** | 数据符合业务规则 | 制品版本号递增、覆盖率在 0-100%、需求与 MR 关联正确 |

### UAT vs 其他层级的区别

```
API 测试：验证接口返回数据正确 → "接口层面没问题"
SIT 测试：验证数据层与服务层一致 → "后端逻辑没问题"
E2E 测试：验证三层联调贯通 → "前后端联调没问题"
UAT 测试：验证用户感知的功能场景 → "用户会满意吗？数据全面准确吗？"
```

UAT 的独特价值：站在**用户视角**评估系统的**业务价值交付质量**，而非技术质量。

### 测试什么

- 完整业务流程（端到端用户故事）
- 验收标准逐条确认（功能/数据全面性/数据准确性/业务正确性）
- 生产级环境验证
- 非功能性需求（性能、安全、可用性）

### 发布门禁标准

| 指标 | 绿灯（可发布） | 黄灯（有条件） | 红灯（禁止发布） |
|------|-------------|--------------|--------------|
| SIT 通过率 | 100% | 70-89% | < 70% |
| P0 Bug | 0 | 0 | ≥ 1 |
| P1 Bug | 0 | 已知且可控 | 未修复 |
| 核心指标误差 | < 1% | < 5% | > 5% |

## 层级间关系与不可替代性

### 依赖关系图

```
UT（无外部依赖）
 ↓ 如果通过 → 函数逻辑正确
API（依赖运行中的服务 + 测试数据）
 ↓ 如果通过 → 接口契约 + 业务数据正确
SIT（依赖真实 DB + 运行中的服务）— 数据层 + 后端服务层联调
 ↓ 如果通过 → 后端服务层逻辑正确
E2E（依赖完整部署环境）— 数据层 + 后端 + 前端三层联调
 ↓ 如果通过 → 三层贯通正确
UAT（依赖生产级环境）— 用户可感知功能场景验证
 ↓ 如果通过 → 功能/数据全面准确，可以发布
```

### 不可替代性矩阵

```
UT 无法替代 SIT：Mock 无法发现集成问题
SIT 无法替代 E2E：SIT 不含前端层，无法验证三层贯通
E2E 无法替代 UAT：自动化无法验证"数据全面准确"
UAT 无法替代 UT：用户视角无法定位具体函数错误

每一层都有独特价值，缺少任何一层都会留下盲区。
```

### 失败时的定位策略

| 现象 | 定位方式 | 负责层级 |
|------|---------|---------|
| 函数返回错误 | 查看 UT 日志 | UT |
| API 返回 4xx/5xx | 检查请求参数和 handler | API |
| API 返回数据不正确但 HTTP 200 | SIT 交叉验证：查 DB 对比 | SIT |
| 页面显示异常但 API 正确 | 检查前端渲染逻辑 | E2E |
| 功能不符合用户需求 | 业务流程审查 | UAT |

## 实战案例：SIT 交叉验证

### 案例 1：source_map 类型过滤

**场景**：source_map API 对非 app 类型制品应返回空 + warning

**SIT 交叉验证**：
1. 数据层：查 DB 确认 pkg 制品存在（`SELECT * FROM aip_artifacts WHERE type='pkg'`）
2. 服务层 A：不带 type 调 source_map（DB 有数据 → 应返回依赖树）
3. 服务层 B：带 type=pkg 调 source_map（类型过滤 → 应返回空 + warning）
4. 交叉断言：不传 type 有数据 + 传 type=pkg 返回空 → 证明过滤器在过滤已有数据

**定位结论**：如果 DB 有数据但 API 始终返回空 → 服务层查询逻辑有 bug

### 案例 2：app 制品源码追溯

**场景**：app 类型制品的 source_map 应包含 commit 节点

**SIT 交叉验证**：
1. 数据层：查 `aip_commit_artifacts` 确认 app 制品有 commit 关联
2. 服务层：调 source_map API（type=app）获取依赖树
3. 交叉断言：DB 有 commit-artifact 关联 → API 依赖树必须包含 type=commit 节点

**定位结论**：如果 DB 有关联但 API 无 commit 节点 → 服务层数据映射有 bug
